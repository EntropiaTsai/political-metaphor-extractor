# 人工後審與可報告的統計口徑

pipeline 產出的是候選，不是結論。這份文件說明如何複審，以及哪些數字可以寫進論文、怎麼寫才不會被挑戰。

## 為什麼一定要人工複審

`mapping_valid=1` 只代表「target 與 source 都有值且都在白名單內」。它是**格式檢查**，完全不保證那個映射在語言學上站得住腳。

`stability_check.py` 量的是重跑的一致性。模型可以穩定地重複同一個錯誤——高一致性和高正確率是兩件事。

所以能支撐結論的只有人工複審。下面的流程是原始專案實際用過的。

## 複審表怎麼開

從 `hierarchy.csv` 匯出複審用的 CSV，保留這些欄位供判讀：

`record_id`、`evidence`、`tenor`、`vehicle`、`ground`、`target_domain`、`source_domain`、`mid_source`

再加三個空欄給複審者填：

| 欄位 | 值 | 意義 |
|---|---|---|
| `tvg_ok` | 1 / 0 | 這是不是真的隱喻，Tenor/Vehicle/Ground 是否成立 |
| `mid_mapping_ok` | 1 / 0 | 中層標籤是否恰當 |
| `note` | 自由文字 | 判 0 的理由，或建議改成什麼 |

分成兩個獨立欄位很重要。「不是隱喻」和「是隱喻但分類錯」要分開統計，因為它們指向不同的修正動作，而且審查人一定會問這兩個數字。

## 判讀準則

依序檢查四件事，任何一項不過就判 `tvg_ok=0`：

**這是隱喻還是代稱？** 只有指稱功能、沒有新的跨域屬性映射的綽號，不算。這是最大宗的假陽性。

**Ground 撐得住嗎？** Ground 必須說明 Tenor 與 Vehicle 之間**實際共享的屬性**。如果 Ground 寫的是「負面評價」「不好的行為」這種空話，這筆多半是把罵人詞誤判成隱喻。

**Tenor 對得上語意焦點嗎？** 字面主詞是人但批評核心是其言論時，Tenor 應該是言論。標成人物就是錯的。

**證據句切題嗎？** 離題插話、日常字面抱怨要排除。

`mid_mapping_ok` 另外看：層級有沒有混淆（角色類誤標成場域類）、粒度是否合適、有沒有落進殘差桶。

## 複審規模

全量複審最好，但不現實。務實的做法：

- **語料 500 筆以下**：全量複審。
- **500 筆以上**：分層隨機抽樣，每個 macro source domain 至少抽 30 筆，小的域全查。報告時寫清楚抽樣方式與每層的樣本數。

不要只抽高信心的那些。`confidence` 是模型自評，跟正確率的相關性不可靠。

**雙人複審**：如果有兩位以上標註者，讓他們獨立標同一批（至少 50 筆重疊），算 Cohen's kappa 並報告。這個數字對審查人的說服力遠高於任何自動指標。單人複審就誠實寫單人，不要含糊帶過。

## 複審結果怎麼回饋

複審不只是打分數，發現的問題要變成三種修正：

**個案修正**——直接把該列的 `mapping_valid` 改成 0，或改掉 domain。適用於零星錯誤。

**規則修正**——同類錯誤出現多次時，寫進 `hierarchy_rules.yaml` 的中層規則，或加進 `target_merge`。原始專案就是這樣把 `支持者群體`、`選民`、`群眾` 合併成 `政治群眾`。

**prompt 修正**——系統性的判斷偏差（例如一直把代稱當隱喻）要回頭改 `extract_system.md` 的排除規則或 few-shot，然後**重跑**。這一步很痛但省不掉；只在下游修，錯誤會在下次跑新語料時原樣重現。

改了 prompt 就要重跑並重新複審。不能拿舊的複審結果去背書新的輸出。

## 可以報告哪些數字

以原始專案為例，四個層層收窄的數字：

| 數字 | 值 | 意義 |
|---|---|---|
| 有效映射 | 591 | `mapping_valid=1`，只是格式檢查 |
| 整筆可接受 | 364（61.6%） | `tvg_ok=1`，嚴格口徑 |
| 中層可接受 | 462（78.2%） | `mid_mapping_ok=1` |
| 乾淨中層 | 454（76.8%） | 中層可接受且非殘差桶 |

分析用的是 454 筆。

**四個數字都要報。** 只報 454 而不交代它從 591 怎麼收窄來的，會被質疑挑資料。把漏斗攤開來反而顯得方法嚴謹。

分母是誰也要寫清楚。上表的百分比分母都是 591（有效映射），不是原始語料則數，也不是抽出來的候選總數。三者差很多，混用會出事。

## 不要這樣寫

**不要把穩定性當準確率。** 「Jaccard 一致性 0.82」不能寫成「準確率 82%」。正確寫法是分開兩句：重跑一致性 0.82，人工複審可接受率 76.8%。

**不要略過被丟棄的資料。** 白名單擋掉的標籤、殘差桶、複審判 0 的，都要有數字。

**不要宣稱模型「發現」了隱喻。** 模型產生的是候選，人工複審後才是資料。方法章節的措辭要反映這一點。

**跨組比較要用比例。** 兩組語料規模不同時比絕對數毫無意義。`stats_*.csv` 的 `ratio` 是組內佔比，用它。組間差異要不要做顯著性檢定，取決於你的研究設計，但至少不能只憑絕對數就宣稱「上升」。

## 方法章節該交代的

- 語料來源、時間範圍、篩選條件、分析單位如何切分
- 模型名稱與版本、temperature、兩階段的設計理由
- taxonomy 如何決定（從資料歸納還是既有理論）
- 中層規則如何制定、殘差如何處理
- 複審方式：全量或抽樣、幾人、如何處理歧見、kappa
- 完整的收窄漏斗
- 穩定性檢查的設定（樣本數、重跑次數、seed）與結果

`config.yaml`、`taxonomy.yaml`、`hierarchy_rules.yaml` 三個檔案本身就是最好的附錄，直接附上比用文字描述精確得多。
